# ADR 0005: Rust/WASM execution for generated Agent code

- Status: Accepted
- Date: 2026-11-20

## Context

The existing Agent providers run native tools through the host-owned MXC MCP server. That path is appropriate for Node.js, Python, Git, npm, and other real development tools, but it is not an appropriate execution target for arbitrary code generated by an LLM.

Provider SDK permission callbacks are not an execution sandbox. Generated native Rust binaries must never be executed directly on the user's host.

## Decision

Add a separate `execute_rust` capability to the existing sandbox MCP server. It is available only when a compatible Rust toolchain and Wasmtime CLI are bundled with the application or explicitly configured for development.

The execution pipeline is:

1. Electron Main authorizes the MCP tool call through the existing provider permission flow.
2. The trusted MCP helper validates source and input sizes, creates an isolated run directory, and snapshots the selected workspace.
3. Snapshot creation excludes symlinks, hard-linked files, VCS metadata, dependency/build output, credential directories, and common secret files. The initial implementation has explicit file-count and byte limits.
4. The helper writes a fixed Cargo manifest, lockfile, SDK dependency, and entry point. The model supplies only the Rust module source and JSON input.
5. The generated module is compiled to `wasm32-wasip2` using an offline, locked Cargo build. The crate root uses `#![forbid(unsafe_code)]`; no model-supplied manifest, build script, proc macro, or third-party dependency is accepted.
6. Wasmtime executes the component with only the staged workspace preopened as `/workspace`. WASI environment variables and network capabilities are not inherited or granted.
7. Wasmtime uses its pooling allocator with one component instance, up to four core instances, one memory and up to two tables, a 256 MiB maximum linear memory, up to two tables, each limited to 100,000 elements, a 100,000,000 instruction-fuel budget, a 1 MiB Wasm stack, and a 60-second Wasmtime timeout. WASI environment inheritance, stdin, HTTP, TCP, UDP, and DNS lookup are explicitly disabled; host calls have a 10,000,000 fuel budget, the guest may hold at most 256 WASI resources, and component handles are capped at 10,000. MXC also imposes a 60-second wall-clock timeout. Both compiler and runtime processes are launched through MXC with write access restricted to the current run directory and read-only access to the bundled toolchain and SDK.
8. The helper computes a file-level diff. A separate `apply_rust_changes` tool checks for concurrent workspace changes and requires a separate provider approval before applying the diff.

The existing `run_command` tool remains the native execution route. Rust/WASM does not replace MXC.

## Capability boundary

The initial SDK is intentionally small and has no external Cargo dependencies. It provides workspace-relative file operations, task input, result output, and logging. Guest code can use Rust's standard library, but it only sees the preopened snapshot and receives no host environment or network access.

The WASI preopen is not the only boundary: the Wasmtime process itself runs in MXC with write access only to the run directory. This limits the impact of a runtime escape to the isolated run directory and the explicitly read-only toolchain/system paths.

## Packaging

The Rust host toolchain, `wasm32-wasip2` standard library, Wasmtime CLI, and SDK are placed under Electron `extraResources`, outside ASAR. The packaging script accepts platform-specific prebuilt toolchain/runtime paths. Release packaging must fail if these resources are missing; ordinary development builds may omit the optional feature.

The packaged Wasmtime CLI must be at least 50.0.1. Version 50.0.0 is rejected because it is affected by the October 2026 component-resource denial-of-service advisory (CVE-2026-126407). The Rust toolchain must support `wasm32-wasip2` (Rust 1.85 or later). Exact versions are recorded in the packaged manifest.

## Consequences and limitations

- The first implementation is a constrained code-execution backend, not a general-purpose Rust development environment.
- It does not support arbitrary Cargo dependencies, build scripts, procedural macros, shell commands, native FFI, or network access.
- The SDK's safe path helpers are convenience APIs, not the security boundary. WASI preopens and MXC enforce the boundary.
- Snapshot copying is deliberately conservative. Symlinks, hard-linked files, and special files are skipped; empty-directory changes are not represented in the initial diff. The 100 MiB snapshot cap is checked before and after execution, not enforced as a live OS disk quota, so guest code can temporarily consume more space until the runtime timeout and cleanup.
- The host applies changes only after a second approval and rejects files changed concurrently since snapshot creation.
- MXC Windows `base-container` is not an AppContainer or VM. macOS uses Seatbelt. Neither is described as VM-level isolation.
- Runtime escape resistance still depends on current Wasmtime and MXC security fixes. Both must be updated and tested against supported OS versions.

## Rollout

The feature is initially opt-in through bundled resources. It must not be advertised as available if compiler/runtime resources are absent. macOS ARM64 and Windows x64 integration tests are required before enabling it in release builds.
